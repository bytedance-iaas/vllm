# GLM-5.3 TK300 Prefill and H20 Decode

The `poc_tk300_h20` branch contains the common vLLM source used by the
validated GLM-5.3 2P4D deployment. Build one image for both roles and select
the role through launch arguments. Prefill retains the original TK300
2P2D optimizations. Decode uses DeepEP v2 low-latency communication with
DBO and MTP5 on four eight-GPU H20 nodes (TP1, PP1, DP32/EP32).

## Source and image dependencies

The runtime source is pinned by the servingkit overlay manifest in
[`glm-5.3-tk300-2p4d`](https://code.byted.org/infcp/servingkit/tree/355d598895d2d439fd43bcde30482d82da3e7318/vllm/glm/glm-5.3-tk300-2p4d).
That deployment includes launch scripts, the router, and the common image
Dockerfile. The manifest SHA256 is
`47e01340d4767fda48d71696cc2cc0bbf32bc947d0a0e850c0cd39e4938c4765`.
Its 35 vLLM target-file hashes match this branch. The unmodified vLLM base
is `4ba787ec9959e566d3b587a796dff07673324da5` (version `0.33.0`).

FlashInfer is a separate required dependency. The validated base is
`flashinfer-python==0.7.2.post1`, source commit
`beabf5004585b03da60e927bbb803acbaa62fe36`, with the nine-file SM120 DSA
indexer overlay selected from
`1de96ee58a5fbde3a6dab621613151447f75d36c`.
Use `files/overlay/flashinfer.patch` from the same servingkit revision.
Its SHA256 is
`827eab828e76e49500f9b13b669e945bc8e59c24f666eeaeac9e2fe8bee4bfef`.
The per-file target hashes in the manifest define the required subset.

The tested image environment also supplies DeepEP v2, NVSHMEM, DeepGEMM,
FlashMLA and NIXL/UCX. Preserve those dependencies when building an image
from this branch. Both roles must report the same vLLM version because
NIXL includes it in compatibility checks.

## ByteIAAS wheel and image build

Run the **ByteIAAS TK300 H20 Build** workflow
(`.github/workflows/byteiaas-release-dev.yml`) with the workflow ref set to
`poc_tk300_h20`. It is manually triggered and has two dependent jobs:

1. `build-wheel` invokes the existing `docker/Dockerfile` `build` target
   once, with CUDA 13.0.3, Python 3.12 and GPU architectures `9.0 12.0`.
   It uploads one vLLM wheel, its checksum and the source commit SHA.
2. `build-image` downloads that same-run artifact, checks its SHA and
   checksum, and uses `docker/byteiaas.Dockerfile` to install the wheel
   over an existing ByteIAAS runtime image. It does not invoke the source
   build again. DeepEP, NIXL, FlashInfer and other dependencies come from
   the selected base; pip dependency resolution is disabled and installed
   dependency compatibility is checked.

The workflow uses the existing ByteIAAS self-hosted wheel/image runners,
proxy and Docker Hub mirror. Configure repository variables
`VOLCENGINE_CR_REGISTRY`, `VOLCENGINE_CR_NAMESPACE` and optionally
`VOLCENGINE_CR_REPOSITORY` (default `vllm`), plus the
`VOLCENGINE_CR_USERNAME` and `VOLCENGINE_CR_PASSWORD` secrets.
The optional `image_tag` input defaults to `poc-tk300-h20-<12-char SHA>`.
The workflow publishes a single linux/amd64 OCI image.

`base_image` defaults to the original pinned ByteIAAS image above. A base
must match the wheel's PyTorch/CUDA/Python ABI and contain the required
serving dependencies. For optimized TK300 Prefill it must also contain
the separately pinned nine-file FlashInfer overlay; the original base
alone does not supply that overlay. A chart-built common image can be
used as the base to retain the FlashInfer overlay. The Dockerfile removes
its old `/opt/tk300-overlay/vllm` directory so it cannot shadow the newly
installed wheel, while retaining `/opt/tk300-overlay/flashinfer`.

For a local image build, put the previously built wheel in a directory
with `wheel.sha256` (relative wheel filename) and `source-commit`, then run:

```bash
docker buildx build --load --platform linux/amd64 \
  -f docker/byteiaas.Dockerfile \
  --build-context byteiaas-wheels=/path/to/wheel-artifact \
  --build-arg BASE_IMAGE="$BASE_IMAGE" \
  --build-arg VLLM_BUILD_COMMIT="$(git rev-parse HEAD)" \
  -t vllm:tk300-h20 .
```

The chart's overlay installer expects original base-file hashes. An image
with this branch already installed needs a corresponding chart image and
installation-mode update so the base patch is not applied twice. The
existing chart Dockerfile builds a shared image from the pinned base and
its overlays. Do not assume the current `overlayInImage` option recognizes
an arbitrary source-built image without checking its startup validation.

## Complete FlashInfer source image

The original build path remains available when `flashinfer_commit` is empty.
For a complete-source image, provide a frozen `flashinfer_commit` from the
`bytedance-iaas/flashinfer` integration branch `poc_tk300_h20` and the matching
`flashinfer_ref`. The workflow builds its full wheel with the qualified base
ABI and installs that wheel together with the same-run vLLM wheel using
`docker/byteiaas-full-source.Dockerfile`. It removes both old package overlays
and writes `/opt/byteiaas/source-provenance.json` with source revisions,
package versions and installed file hashes. Native communication dependencies
remain from the selected qualified base.

The complete-source entrypoint uses the base system Python environment, where
both new wheels are installed. Its explicit path and neutral working directory
prevent an inherited development virtualenv or source checkout from shadowing
the installed packages. Dependency checks compare conflicts before and after
installation and reject changes to that set. Existing base conflicts are
recorded in `/opt/byteiaas/{base,source}-dependency-conflicts.txt`; this does
not qualify an arbitrary base or repair its dependencies.

The deployment must explicitly choose complete-source image mode so the old
base patches are not applied to the newly installed packages. Verify both
source revisions and installed hashes before serving. Keep the original
image/overlay deployment as a rollback option until this image is qualified.

The optional [TK300 MoE cache loader](../features/tk300_moe_cache.md) is part
of the vLLM package. Its manifest/native entries remain deployment artifacts.
Enable it only on the qualified L recipe after checking actual target
FlashInfer metadata and numeric behavior; old cache version stamps cannot be
edited to bypass validation. The loader stays disabled on Decode and C.

## Role configuration

Use `VLLM_USE_V2_MODEL_RUNNER=1` on both roles. The launch scripts in the
chart define process placement, ports, and distributed rendezvous.

| Setting | TK300 Prefill | H20 Decode |
| --- | --- | --- |
| Checkpoint mounted at `/model` | GLM-5.3 NVFP4 | Original block-FP8 GLM-5.3 |
| Attention | `FLASHINFER_MLA_SPARSE_SM120` | `FLASHMLA_SPARSE` |
| KV dtype and block size | `fp8_ds_mla`, 64 tokens | `fp8_ds_mla`, 64 tokens |
| All-to-all | `allgather_reducescatter` | `deepep_low_latency` |
| MoE kernel | As specified by Prefill recipe | `deep_gemm` |
| Execution | Eager, PP/PCP per chart | `FULL_DECODE_ONLY`, DBO enabled |
| MTP | 5 tokens | 5 tokens |

The Prefill kernel configuration is:

```json
{
  "enable_flashinfer_autotune": false,
  "sparse_indexer_topk_backend": "flashinfer_sm120",
  "mla_bmm_backend": "flashinfer_cudnn",
  "enable_sparse_indexer_remap_reuse": true,
  "enable_pp_indexer_handoff": true
}
```

`mla_bmm_backend` defaults to `auto`, which uses `torch.bmm` with its
original output layout. The explicit `flashinfer_cudnn` backend uses the
optimized full-chunk MLA BMM path and tunes its two shapes during weight
post-processing. Remap reuse and PP TopK handoff default to disabled.
The experimental `enable_idle_dp_draft_skip` option also defaults to
false and is not required by the deployment.

Decode uses `--enable-dbo`, Decode/Prefill DBO thresholds of 32/512,
and `VLLM_DBO_COMM_SMS=0`. The runtime isolates per-microbatch sparse
attention buffers and metadata. Uneven batches fall back from DBO when
they cannot satisfy the uniform FULL Decode requirements.

This snapshot restores the validated hidden/residual PP boundary ABI and
gates sequence parallelism to PP1. It intentionally supersedes the
`d565d4d4ec` PP/SP implementation in `poc/tk300`. The TK300 TP1 Prefill
recipe is validated; the earlier TP4/PP2 sequence-parallel behavior is
not preserved as a supported recipe by this import. PCP drafter
resynchronization from `a13537bf01` remains included.

## KV handoff over vRDMA

Use NIXL Push and set `TK300_GLM53_NIXL_COMPAT=1` on both roles. This
opt-in compatibility alias applies only when the model is mounted at
`/model`, its model type is `glm_moe_dsa`, KV dtype is `fp8_ds_mla`, and
the transfer mode is `push`. It aliases the two packed MLA attention
backend names. Version, shape, dtype and other compatibility factors
remain checked. The environment variable defaults to disabled.

The validated vRDMA route uses UCX device `mlx5_0:1`, GID index 3 and
`UCX_TLS=rc,cuda_copy`, with GPU Direct RDMA enabled. NIXL's vRDMA device
is configured independently of the NCCL and NVSHMEM RoCE devices used
for expert communication. Preserve the chart's per-role HCA mapping.

The chart includes the router integer-rendering fix needed to retain
large integer fields in launch configuration. Router configuration and
FlashInfer sources remain in their owning packages.

## Optional Prefill diagnostics

Set `VLLM_ENABLE_PREFILL_PROGRESS=1` to enable
`POST /internal/prefill/progress`. Send a JSON object with `request_ids`,
a list of at most 128 strings, each at most 256 characters. The endpoint
returns per-engine progress; it returns 404 when disabled (the default).

The experimental `additional_config.shared_ep_budget` profile is absent
by default. Enabling it requires calibrated stage costs that match the
DP/PCP/PP topology, FCFS scheduling and chunked Prefill. Use profiles
calibrated with the same connector configuration as serving.
`start_prefill_timing` and `read_prefill_timing` worker RPCs provide
bounded diagnostic CUDA-event samples; they do not represent isolated
kernel time or automatically guarantee a latency target.

## Validation scope

The final common runtime was previously validated on two TK300 Prefill
nodes and four H20 Decode nodes, including real cross-role KV handoff,
a Prefill comparison against the original recipe, and one LongBench
Decode comparison against the DeepEP v2 + DBO reference. The source
import preserves the 35 validated vLLM files byte for byte. Python
compilation and whitespace checks were rerun for the import; GPU
benchmarks were not repeated for the Git commit split.

The imported snapshot retains one Ruff `SIM102` style finding in NIXL
metadata and formatting differences in four files to preserve those
hashes. These are recorded limitations of the source import.
